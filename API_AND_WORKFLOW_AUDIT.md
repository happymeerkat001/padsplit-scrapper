# API and workflow audit

Audit of the repository working tree, 2026-11-04. This records code paths and local test evidence; it does not establish that the deployed site or deployed Firebase rules match the repository, that production credentials exist, or that any real service operation succeeds. No production data, calls, messages, or device operations were performed for this audit. In this document **verified locally** means the cited tests exercised the specified behavior in mocks or emulators; it is not an end-to-end production claim.

## Open evidence and release limitations

- Proposed Firestore rules and app changes are local-branch artifacts until deliberately deployed; historical public data and the current Pages deployment require owner-led containment, rotation and history remediation.
- The transaction-based restore prevents concurrent overwrite in its final compare/write. Its pre-restore history snapshot is a separate write, so a cancelled/conflicted attempt may leave a harmless extra history entry; ordinary saves still do not detect another editor's concurrent update.
- `padsplit_scraper/leak_alert_bland.py:drain_result_queue` now requires a create-only Admin Firestore claim before a live Quo result send. A second updated worker, timeout, or crash cannot trigger an automatic resend while the claim exists; invalid preflight configuration does not consume a claim. Uncertain results and older pending/queue records require manual reconciliation, and a crash after claiming but before sending can leave an unsent result needing review. This is at-most-once behavior, not guaranteed delivery. Before enabling it, stop old workers that do not honor claims, review existing queue entries and verify the Admin account can write `leak_alert_result_claims`. Never automatically clear a claim without checking the provider. Tests use fake stores and no real delivery; production IAM, provider outcomes and concurrent deployment remain unverified.
- Internal notes, vendors, templates and task collections are owner-restricted by local rules, but their full input schemas and lengths are not enforced server-side; this remains a known gap rather than a verified production workflow.
- Emulator checks do not establish real authorized browser workflows, production IAM, expiration behavior, outbound provider delivery, device state or private snapshot retention. See `PRIVATE_SNAPSHOT_DESIGN.md`, `DATABASE_REFERENCE.md` and `PRODUCTION_REMEDIATION.md` for prerequisites.
