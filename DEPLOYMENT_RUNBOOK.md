# Vercel and VPS deployment preparation

Status: **not ready for a live rollout**. The API and PostgreSQL work is in development and the existing dashboard still reads Firestore directly. The release build deliberately fails until those paths are replaced, the frontend consumes its runtime configuration, preview targets are isolated, and the private-content scan passes. Preparing a Vercel deployment does not erase the known exposure in the existing public Pages site or Git history. ## VPS staging template

`deploy/compose.yaml` is a reviewed starting template, **not a tested live deployment**. It publishes no database or API host ports. PostgreSQL uses a dedicated named volume, a private internal Docker network, and a bootstrap admin password supplied from an external file. The API has an isolated database network, a separate outbound network for Firebase certificate/identity checks, and a dedicated external proxy network. Its root filesystem is read-only, Linux capabilities are dropped, process count is bounded, access logging is disabled, and container logs have limits. Create a separate database role with only the grants required by the application; never put the bootstrap administrator credentials in the API connection string.

The API uses `SELECT ... FOR SHARE` to serialize authorization checks with permission revocations. PostgreSQL requires an appropriate `UPDATE` privilege for these row locks, even when the application does not update the locked row. Migration 006 adds constrained `auth_lock_guard` columns for narrowly scoped column-level grants; local restricted-role and concurrent-revocation tests passed. Migration 011 adds the read-only `team_access_version` column needed for the owner roster and optimistic membership edits. A DBA must review and apply the grants described in `MIGRATION_RUNBOOK.md` and verify this boundary on the actual staging VPS before any release. Do not grant broad update access to memberships or roles as a shortcut. The team service intentionally requires both database connection strings to resolve to the exact same configured host and port, as well as checking server start identity, database name, and table OIDs; equivalent hostname aliases fail closed until both are configured identically.

Caddy runs **inside an existing container**. The API's loopback is not Caddy's loopback; do not configure Caddy to connect to host `127.0.0.1` without a separately verified network design. After inspection and explicit operational review, the API and existing Caddy could join a dedicated new Docker network named by `PADSPLIT_CADDY_NETWORK_NAME`; the proposed API alias is `padsplit-operations-api`. Configure a new HTTPS virtual host in the existing Caddy configuration to reverse-proxy to that alias and the selected container port. Preserve all existing routes and volumes; validate the complete Caddy configuration, reload only through the established process, and verify the existing services remain healthy. Check reverse-proxy request-size, rate, timeout and redacted access-log settings. No host proxy or network has been modified.

Inputs to the compose template, all required and without defaults:

- `PADSPLIT_POSTGRES_IMAGE`: reviewed PostgreSQL image pinned by digest; check the supported major version and persistent-volume upgrade plan.
- `PADSPLIT_DB_NAME`, `PADSPLIT_DB_ADMIN_USER`: isolated database and bootstrap-admin names; choose distinct names.
- `PADSPLIT_POSTGRES_ADMIN_PASSWORD_FILE`: external, owner-readable private password file.
- `PADSPLIT_API_IMAGE`: reviewed API image pinned by digest, built from `deploy/api.Dockerfile` after its dependencies and source have passed review.
- `PADSPLIT_API_ENV_FILE`: external private env file. Its required runtime keys are `DATABASE_URL`, `FIREBASE_PROJECT_ID`, and `API_ALLOWED_ORIGINS`; `API_RATE_LIMIT_PER_MINUTE` is optional. Access-code operations additionally require `PADSPLIT_CODES_KEY` (base64-encoded 32-byte server key) and `PADSPLIT_CODES_KEY_VERSION` (identifier). Store that key separately from encrypted backups and from `PADSPLIT_MIGRATION_KEY`; historical multi-key rotation is not implemented. `DATABASE_URL` must use the restricted application role. Include no secrets in Vercel variables or frontend bundles.
- Team administration is disabled by default. Its optional server settings are `PADSPLIT_TEAM_ADMIN_ENABLE=1` and `TEAM_DATABASE_URL`, a distinct least-privilege database principal. The release builder can emit the public `teamEnabled: true` runtime flag with `--enable-team`. Review `TEAM_POSTGRES_SECURITY.md`, provision and test the actual grants, and verify Firebase lookup before enabling either side.
- `PADSPLIT_FIREBASE_ADMIN_CREDENTIALS_FILE`: external service-account credential file with narrowly scoped identity permissions. Compose mounts it read-only as `/run/secrets/firebase_admin_credentials` and sets `GOOGLE_APPLICATION_CREDENTIALS`; make the file readable by API UID/GID 65532 without making it public. Firebase verification with revocation checking needs appropriate Google IAM access.
- `PADSPLIT_API_CONTAINER_PORT`: an explicitly chosen container-only port after reviewing the proxy network. It is not published on the host.
- `PADSPLIT_DB_MEMORY_LIMIT`, `PADSPLIT_API_MEMORY_LIMIT`: explicit Docker memory limits selected after measuring existing workloads and staging capacity; the template supplies no defaults.
- `PADSPLIT_CADDY_NETWORK_NAME`: a dedicated existing external Docker network agreed with the proxy administrator.

The API image build requires a **reviewed digest-pinned Python 3.12 base** as build argument `PYTHON_BASE_IMAGE` and installs exact-version `backend/api/requirements.lock`. Its accompanying Dockerfile-specific ignore file restricts build context to the API code, lock file, and only the two storage modules required for encrypted code operations; migration inputs and private data are excluded. Check Docker/Compose support and inspect the effective context before building. The lock has exact versions but does not currently contain integrity hashes. Docker execution and health checks have not been tested here. The API uses one process: its current in-process rate limiter is not shared across workers or replicas, so enforce an independently reviewed proxy rate limit before exposing it.

The API `/health/live` checks process liveness. `/health/ready` requires PostgreSQL connectivity and a minimum table/column contract, using system-catalog metadata without querying private rows or requiring access to `schema_migrations`. The supplied Compose API healthcheck uses `/health/ready`. This check is deliberately not a full migration checksum, role-grant, Firebase, key, source-data or provider readiness test; a staging rollout must separately verify those dependencies before directing traffic. The current migration tool must still verify all migration checksums.

`deploy/systemd/padsplit-collector.{service,timer}.template` are intentionally disabled templates with unresolved account, paths, and schedule. They force collection-only mode, action hooks off, Git publication off, and `PADSPLIT_DISABLE_FIRESTORE_UPLOAD=1`; they also clear Firebase credential variables. The `locked_collector` entry point requires these explicit gates and existing owner-only output, state and lock directories outside the checkout, then runs isolated output under the existing local process lock. The lock prevents overlapping instances only when they use the same host and lock directory; it is not a distributed scheduler lock, and the worker does not yet publish into PostgreSQL. The existing morning and afternoon scripts use different locks, so they are not coordinated by this entry point. Copying or enabling these templates is **not** part of this preparation. Ensure the dedicated service user owns the private directories, verify that no other host or scheduler runs the job, and validate logs, process locking and the worker in a private staging environment. Existing macOS launchd, Apple Messages, Chrome/Google Voice sessions, and related machine-specific automation are not verified on Linux. Never enable calls, messages, door-code rotation, devices, outbound integrations or live schedules merely to test deployment.

## Vercel build and preview

The source pages live under `docs`; `deploy/frontend-assets.json` is the reviewed allowlist, and `deploy/frontend_build.py` creates a standalone static project outside the checkout. `deploy/vercel.json` supplies static routing defaults and basic headers; direct `.html` URLs and `/` should be smoke-tested on the eventual preview. Build environment variables are not automatically pulled from any existing Vercel project. No backend, database, service-account or other private credentials belong in the generated frontend. The build generates `runtime-config.js` containing only the selected public API origin, Firebase browser configuration and environment. Firebase's browser API key is a public project identifier visible to clients, not an Admin SDK credential; security depends on authentication, rules, and server-side authorization. It must belong to the selected environment.

For an isolated staging preview, prepare **separate** staging Firebase and API origins. The command requires their explicit values and also requires the known production Firebase project and origin to enforce separation. For example, with placeholders replaced and a private blocklist file outside the checkout:

```sh
venv/bin/python deploy/frontend_build.py \
  --output /secure/staging/frontend-output \
  --environment preview \
  --review-pages \
  --firebase-project STAGING_FIREBASE_PROJECT \
  --firebase-web-config /secure/staging-firebase-web-config.json \
  --api-origin https://STAGING_API_HOST \
  --production-firebase-project PRODUCTION_FIREBASE_PROJECT \
  --production-firebase-web-config /secure/production-firebase-web-config.json \
  --production-api-origin https://PRODUCTION_API_HOST \
  --private-blocklist /secure/private-values.txt
```

Both Firebase web-config JSON files must contain exactly `projectId`, `authDomain`, and `apiKey` for their respective projects; each auth domain currently must be its default `<projectId>.firebaseapp.com`. They must not contain a service-account key, password, or any other private field. Only the selected environment's public configuration is copied into the generated JavaScript, so verify the project/key association before building. For preview the build also rejects a web key identical to production's. The output path must not already exist or be inside the repository. The private blocklist stays local and is never copied to the artifact. The gate requires HTTPS, rejects userinfo and private-address origins, compares preview and production targets, checks Firebase project literals, rejects hardcoded web keys and direct Firestore SDK usage, checks that each page consumes `PADSPLIT_RUNTIME_CONFIG` and handles the API-mode marker, checks local links against the asset allowlist, and runs the publication guard. It adds `<meta name="padsplit-data-mode" content="api">` to every output page so a missing runtime file can fail closed rather than fall back to legacy production services. This check is a focused defense, not proof that unknown sensitive values are absent. The explicit `--review-pages` option selects the API-only overview and inbox candidates for **preview only** and adds a staging notice to every page; it is rejected for production. A successful preview build does not verify ingestion, historical completeness, source mappings, live authentication, or production readiness. The default build remains blocked by the legacy overview and inbox. Preview isolation also requires independently verifying that the staging backend and database are isolated, because distinct hostnames alone cannot prove that.

After the gate succeeds and a separate staging backend exists, verify the exact new Vercel project and team, configure deployment protection, and deploy a preview only within the user's authorized scope. Do not overwrite `angli-site`, promote to production, purchase a plan, change billing, or embed service secrets. Configure Firebase authorized domains and password-reset return URLs for the reviewed preview only after verifying the intended project and authentication flow. Test direct page links, reload, sign-in, password reset, sign-out, authorization failures, and network calls on the preview; verify no request reaches the production backend or data. Before any eventual production promotion, prepare a cutover and rollback review.

## Encrypted backups and restore rehearsal

`deploy/backup-db.sh` streams a PostgreSQL custom-format dump directly through `age` to a new restrictive-permission `.age` file outside the repository. It fails if the dump or encryption fails and refuses to overwrite an existing archive. `PGDATABASE` must be explicit; use standard `PGHOST`, `PGPORT`, `PGUSER` and a restricted `PGPASSFILE`, not a password in command arguments. Pass only an age **public recipient** as the first argument. Copy the encrypted archive to configured private off-server object storage, apply an approved retention policy, and keep the age identity and storage credentials separate. No object storage account, off-server upload, retention policy, or production schedule has been configured.

`deploy/upload-backup.sh` provides an **off by default** provider adapter interface, with no preset destination or credentials. It requires `PADSPLIT_BACKUP_UPLOAD_ENABLE=1`, `PADSPLIT_BACKUP_ADAPTER` as an absolute path to a reviewed executable, and `PADSPLIT_BACKUP_RETENTION_DAYS` (7–3650). It accepts an existing binary age archive and a non-secret destination identifier without embedded credentials, query, or fragment. The adapter must implement `verify-retention DEST DAYS`, `put-if-absent ARCHIVE DEST SHA256`, and `verify-object DEST SHA256`: retention must be checked before transfer, overwrites rejected, and the remote object checksum verified. Credentials must come from the provider's private credential mechanism, and the adapter must not log them. This is an adapter contract; provider-side immutability and retention still require independent verification. The archive-header check only catches obvious plaintext and is not a cryptographic validation. The offline mock test runs with `venv/bin/python deploy/test_upload_backup.py -q`; it does not contact object storage. Do not schedule uploads until a real provider, retention policy, permission model, and off-server retrieval-and-restore test are reviewed.

`deploy/restore-db.sh` decrypts through a private FIFO and only accepts a local PostgreSQL target named `padsplit_restore_*`; it must be an explicitly created **disposable staging database**. It rejects production-named targets, comma-separated host lists, and `PGHOSTADDR`, `PGSERVICE`, or `PGSERVICEFILE` because they can redirect libpq away from the checked host. `venv/bin/python deploy/test_backup.py -q` rehearses encryption and a restore using fictional data in a fresh local PostgreSQL cluster, checks permissions and plaintext absence, and checks failed dump cleanup. This local test is not an off-server restore or a production disaster-recovery certification. Repeat a protected off-server retrieval and restore exercise after storage and VPS access exist; record the recovery time, counts, checksums and ownership/grants, then delete the staging copy according to the data-retention policy.

## Rollout and rollback

Before production cutover, complete the migration runbook, obtain a source write pause or verified incremental catch-up, compare counts, relationships and fields, and verify the final rehearsal. Keep Firestore and its existing backups intact. Prepare a distinct deployment and confirm health/readiness, authentication, role/property isolation, privacy, endpoint failures, and rollback against the specific versions. On an approved cutover failure, stop the new writers, keep the prior source authoritative, restore the previous frontend routing and service configuration, and reconcile any accepted writes before retrying. Do not delete Firestore data or promote Vercel production during preparation.

### Optional private weather

Weather is disabled by default, including staging. If explicitly approved, set `PADSPLIT_WEATHER_ENABLE=1`, `PADSPLIT_WEATHER_LATITUDE`, and `PADSPLIT_WEATHER_LONGITUDE` in the private API or worker environment. Values must be finite decimal coordinates, within geographic bounds and at most six decimal places. Do not place them in frontend configuration, commits, or public artifacts. Only owners can access the API forecast; scoped users cannot request it.

Enabling weather sends the configured coordinates to the fixed Open-Meteo provider. App responses and application error messages omit coordinates, but operators must review their external network, proxy, and infrastructure logging before enabling it. The API and digest make no weather provider request while disabled. Disable it again by removing the enable flag and restarting the API and relevant workers.
