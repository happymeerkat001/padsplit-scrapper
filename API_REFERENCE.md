# Operations API reference — local implementation

This API is an undeployed foundation. Local API-mode screens include notes, scoped tasks, staging occupancy and provider observations, vendors, templates, codes, reports and history. An inbox prototype remains local-only; the remaining overview and inbox release sources still use Firestore. No Vercel release build or deployment has been completed, and real Firebase owner and report-reader access remain unverified. The browser continues to sign in with Firebase Authentication; this service verifies the Firebase ID token using the Admin SDK with `check_revoked=True`, then reads active roles and property assignments from PostgreSQL. Claims supplied by the browser do not grant roles. The initial owner and any report-only capability must be provisioned by a trusted operator. An owner-only team API is available behind a separate disabled-by-default configuration; see `TEAM_POSTGRES_SECURITY.md`. The Firebase Admin SDK must use credentials for the configured project.

## Configuration

- `DATABASE_URL`: private PostgreSQL connection string. Never expose it to the frontend or logs.
- `FIREBASE_PROJECT_ID`: exact Firebase project ID used for token issuer/audience verification.
- `GOOGLE_APPLICATION_CREDENTIALS`: path to an appropriately scoped Firebase Admin credential when application default credentials are not otherwise available. Do not commit it.
- `API_ALLOWED_ORIGINS`: comma-separated exact allowed frontend origins, with no wildcard. HTTPS is required except explicit loopback development origins.
- `API_RATE_LIMIT_PER_MINUTE`: optional per-user, per-process rate limit, default 60 (allowed range 1–1000).
- `PADSPLIT_CODES_KEY`: base64 encoding of a 32-byte encryption key, distinct from the migration/backup key. Keep it in server-only secret storage, separate from database and backup artifacts.
- `PADSPLIT_CODES_KEY_VERSION`: identifier for the active key; required for code endpoints. Stored data encrypted with a different key version fails closed. A multi-key rotation service is not implemented.
- `PADSPLIT_TEAM_ADMIN_ENABLE`: optional; exactly `1` enables the owner-only team router. It is disabled otherwise.
- `TEAM_DATABASE_URL`: separate restricted team-service PostgreSQL credential, required when the team router is enabled; never expose it to the frontend. See `TEAM_POSTGRES_SECURITY.md` for the necessary separation and limits.

Start after applying the numbered database migrations using `uvicorn backend.api.app:app --host 127.0.0.1 --port <chosen-port> --workers 1 --no-access-log`. The entry point validates required configuration during startup, rejects a Firebase Auth emulator, and performs no outbound integrations. Terminate TLS at a separately configured trusted reverse proxy. Never expose PostgreSQL publicly.

The in-process rate limiter keys on verified user ID, bounds its memory and covers all authenticated routes. It is **not a distributed limiter**. Until an appropriately tested shared limiter exists, run one API worker and enforce independent connection, request-body, and rate limits at the reverse proxy, including limits before authentication. Do not trust client-provided forwarding headers. Configure access and error logging to omit authorization headers, request/response bodies, query strings, and paths containing private IDs; Uvicorn access logs should remain disabled. ASGI request bodies for writes are limited to 16 KiB, including streamed bytes; the proxy should independently enforce body limits and timeouts. An outer HTTP exception boundary returns a generic 503 without re-raising unexpected exception text; after headers have already been sent, it leaves the response incomplete rather than claiming success. This boundary does not replace reviewing server, proxy, startup, and library logging in the target deployment.

The repository takes PostgreSQL row locks while checking user and property permissions. Migration 006 adds constrained guard columns so a database role can be granted only the column-level privileges needed for these locks. Local tests with a separate restricted role denied role, membership and scope changes and verified that concurrent revocation waits for the authorized write. The required DBA grants are documented in `MIGRATION_RUNBOOK.md`; they have not been applied or verified on the VPS. Do not grant broader role or membership update permissions merely to make the queries run.

## Contract

Authenticated routes require `Authorization: Bearer <Firebase ID token>`. Ordinary errors use `{ "error": "..." }`: authentication errors are 401, access denial 403, missing resources 404, version/idempotency conflicts 409, validation errors 422, rate limits 429 with `Retry-After`, and dependency failures 503. Responses use `Cache-Control: no-store`. Idempotency keys are restricted to `[A-Za-z0-9_.:-]`, 1–200 characters; their uniqueness is per authenticated actor across creation routes. Reusing a key with different input returns 409. Pagination defaults to 50, accepts 1–100, and offsets up to 10,000; order is deterministic.

| Method and path | Behavior |
| --- | --- |
| `GET /health/live` | Process liveness; no authentication. |
| `GET /health/ready` | Returns 200 only when PostgreSQL is reachable and the API's minimum required tables and columns exist in the configured search path; otherwise 503. The metadata check does not verify migration checksums, data completeness, database grants, Firebase, encryption keys or external services. |
| `GET /v1/me` | Verified UID, trusted role, and explicitly assigned property IDs. |
| `GET /v1/properties` | Owner sees properties; scoped users see assigned properties. |
| `GET /v1/occupancy` | Paginated, property-scoped staging observations; reports `ingestion: "staging_only"`. |
| `GET /v1/climate?property_id=&limit=&offset=` | Paginated latest staged observations per device, scoped to authorized properties. Returns `ingestion: "staging_only"`; location-to-property bindings require explicit review. No device controls or live ingestion are provided. |
| `GET /v1/provider-tasks` | Paginated, property-scoped, read-only provider task observations; only selected fields are exposed and no provider actions are performed. |
| `GET /v1/provider-discussion-links` | Property-scoped, explicitly reviewed provider-observation to internal-task links; stale or mismatched observations are omitted. Reports `reviewed_links_only` coverage and `staging_only` ingestion. |
| `GET /v1/room-task-links` | Property-scoped links explicitly reviewed for exact current observations; response declares `reviewed_links_only` coverage and `staging_only` ingestion. |
| `GET /v1/report-access` | Indicates whether the authenticated active user is an owner or has an explicitly provisioned report capability. |
| `GET /v1/reports/{id}` | Owner or explicitly granted report reader can read `latest` or `monthly_history` statistics. Returns source JSON as `json` text and its `observed_at` timestamp; returns 404 for absent data. No KPI values are invented by the API. |
| `GET /v1/notes/{id}` | Owner-only note; returns `{id,text,version,exists}`, with version 0 when absent. |
| `PUT /v1/notes/{id}` | Owner-only `{text,expected_version}`; use version 0 only for initial creation. Returns only `{id,version}`. |
| `GET /v1/tasks?property_id=&limit=&offset=` | Owner sees all tasks; scoped users see assigned properties only. Legacy tasks with no property are owner-only. |
| `GET /v1/tasks/{id}` | Rechecks the authenticated user's current property access before returning the requested task. |
| `POST /v1/tasks` | Owner/manager/operator; requires `Idempotency-Key` and `{property_id,title,status,priority}`; returns `{id,version}`. Status is `open`, `in_progress`, or `done`; priority is `low`, `normal`, `high`, or `urgent`. |
| `PATCH /v1/tasks/{id}` | Owner/manager/operator; `{status,expected_version}` changes status while preserving the existing title, or include a nonempty `title` of at most 200 characters to change it explicitly. An explicit null title is rejected. Version mismatch is 409. |
| `DELETE /v1/tasks/{id}?expected_version=N` | Owner or assigned manager; refuses deletion with a 409 when discussion exists. A repeated deletion returns 404 rather than deleting another record. |
| `GET /v1/tasks/{id}/discussion?limit=&offset=` | Scoped read; viewer is permitted. |
| `POST /v1/tasks/{id}/discussion` | Owner/manager/operator; `Idempotency-Key` and `{body,role_label?,status_label?}`; returns only `{id}`. Optional labels are display text, not authorization. Author is the verified identity. |
| `DELETE /v1/tasks/{id}/discussion/{discussion_id}` | Owner/manager/operator with access to the task's property; hides the discussion using a tombstone and writes a redacted audit event. The original record is retained. Repeated deletion returns 404. |
| `GET /v1/inbox/conversations?limit=&offset=` | Read-only property-scoped conversation metadata; unassigned records are owner-only. Returns `ingestion: "not_configured"`. |
| `POST /v1/inbox/search` | Property-scoped search of stored titles, reviewed property names, allowlisted observed names and addresses, and non-deleted message text; JSON body has `q` (up to 100 characters), `unread` (boolean), `limit` (1–100) and `offset` (0–10000). Rows include only allowlisted observed display fields and a preview of the latest stored message; the preview is null when that message is deleted. Unknown unread states are excluded when filtering unread. Search terms belong in the body rather than URL access logs. The database query has a two-second timeout. |
| `GET /v1/inbox/conversations/{id}/messages?limit=&offset=&order=&before=` | Read-only messages after checking and locking the conversation's property. `order` is `asc` (default, oldest first) or `desc` (newest first); unknown timestamps sort last. Optional `before` is an authorized message ID from this conversation and requires `order=desc` and `offset=0`. Full descending pages return `next_before`; invalid or mismatched anchors are rejected. Anchors prevent new messages ahead of a page from shifting older pages, but concurrent updates or deletions can still affect coverage. Attachment locations and unsafe filename metadata are omitted; attachment content and outbound messaging are not available. |
| `GET /v1/vendors?limit=&offset=` | Owner-only global records; no property scope exists in these records. |
| `GET /v1/templates?limit=&offset=` | Owner-only global records, returning `{id,name,body,version}`. |
| `POST /v1/vendors` | Owner-only `{name,specialty,contact,location}`, with `Idempotency-Key`; returns `{id,version}`. |
| `PATCH /v1/vendors/{id}` | Owner-only `expected_version` plus at least one changed vendor field. Omitted fields, including missing, null and unknown migrated fields, are preserved; an explicitly supplied null or empty string is a deliberate change. |
| `DELETE /v1/vendors/{id}?expected_version=N` | Owner-only, conflict-safe deletion. |
| `POST /v1/templates` | Owner-only `{name,body}`, with `Idempotency-Key`; returns `{id,version}`. |
| `PATCH /v1/templates/{id}` | Owner-only `{name,body,expected_version}`. |
| `DELETE /v1/templates/{id}?expected_version=N` | Owner-only, conflict-safe deletion. |
| `GET /v1/properties/{id}/codes` | Owner-only metadata and masked values; no plaintext returned. |
| `GET /v1/codes/schema` | Owner-only validated encrypted layouts and corresponding versions, read from one database snapshot. Incomplete or mismatched layout/value sets fail closed; code values are never included. |
| `POST /v1/properties/{id}/codes/reveal` | Explicit, owner-only reveal; returns plaintext to the authorized caller, uses no-store, and records an audit event without the values. Never log or cache the response. |
| `PUT /v1/properties/{id}/codes` | Owner-only `{fields,expected_version}`; use version 0 only for first creation. Encrypts with AES-GCM using property, version and key version as associated data. Returns version only. |
| `GET /v1/properties/{id}/codes/history?limit=&offset=` | Owner-only history metadata; no code values. |
| `POST /v1/properties/{id}/codes/history/{history_id}/reveal` | Explicit owner-only reveal of one historical code map; records a redacted audit event. |
| `POST /v1/properties/{id}/codes/history/{history_id}/restore` | Owner-only `{expected_version}`. Checks current version, preserves the previous encrypted state in immutable history, and restores in one transaction. Returns version only. Unknown legacy source versions and stale writes fail closed. |

Task changes, discussion creation, notes, vendor/template changes, explicit code reveal, code saves and restores create server-side redacted audit events inside their transactions. These events omit task titles, notes, vendor fields, template bodies, discussion text, tokens and code values. Audit viewing, failed-attempt audit events, key rotation and an audited account/role provisioning endpoint remain unimplemented. Notes, code save and restore are protected against accidental repeats by version preconditions: a retry after a successful write returns 409 and requires a fresh read rather than silently repeating it.

## Boundaries and checks

`GET /v1/occupancy` provides scoped, paginated observations from the staging projection and reports `ingestion: "staging_only"`; it does not establish fresh collection. An experimental local-only inbox reads scoped PostgreSQL records; recurring ingestion is not configured and it has not replaced the existing inbox in release navigation. Provider sends, schedules, full property details and complete dashboard migration are not implemented. In local API mode, vendors poll the API and keep edits on conflict; templates map only the canonical `template_shared_0` through `template_shared_8` slots, disable missing slots, and reject unexpected or duplicate IDs rather than hiding records. Templates and notes use version checks and preserve drafts. Codes remain hidden until explicitly revealed; changed fields are merged into the decrypted baseline. Ordinary history returns metadata only; historical reveal is explicit, and restore uses the expected current version. A staging-only history projector supports validated source versions; `source_version` is an encryption context, not a historical sequence. Raw Firestore exports and attachments are not served. No production cutover is complete.

API mode is selected explicitly by a build marker and runtime configuration containing `dataMode: 'api'`, `environment`, `apiOrigin`, and a complete environment-specific Firebase web config. A missing or invalid configuration fails closed; it does not fall back to Firestore. Preview cannot use the production Firebase project. Legacy source behavior remains available only when API mode has not been selected. The release guard continues to block the shared site while legacy Firestore paths and other unmigrated pages remain in the release artifacts.

Synthetic DOM checks for the API-mode vendor, template and codes pages can be run after installing `linkedom@0.18.15` outside the checkout: set `PADSPLIT_UI_TEST_MODULES` to that installation's absolute `node_modules` directory and run `node tests/ui/vendor_api_dom.cjs`, `node tests/ui/templates_api_dom.cjs`, `node tests/ui/codes_api_dom.cjs`, and `node tests/ui/codes_page_api_dom.cjs`. `node test_vendor_api_mode.mjs`, `node test_template_api_mode.mjs`, and `node test_codes_api_mode.mjs` run their mapping and configuration checks without that dependency. These checks mock Firebase and the API; they do not verify a real browser session or deployment.

Run offline HTTP tests with `python -m unittest backend.api.test_api backend.api.test_codes_api backend.api.test_shared_api backend.api.test_notes_api -q`. Run PostgreSQL tests only against a disposable loopback database whose name begins `padsplit_stage` by setting `PADSPLIT_API_TEST_DATABASE_URL` and running `python -m unittest backend.api.test_postgres backend.api.test_codes_postgres -q`. The tests create synthetic data, verify permission denials, version conflicts, concurrent idempotent creates, encrypted code history, and redacted audit events; they do not verify live Firebase identity or production data.

### Private weather

`GET /v1/weather` requires an authenticated owner. When disabled it returns `status: not_configured` and an empty `days` array; when enabled it returns daily temperatures without coordinates. Other roles receive 403. Provider failures return a generic 503. This endpoint does not affect the rest of the session when weather is unavailable.
