# Inbox attachment delivery boundary

The current inbox is **metadata-only**. It cannot retrieve or serve attachment content. The provider message-list query requests an attachment ID and location, but the collector deliberately discards `location` before creating an encrypted capture. The staging projection hashes attachment IDs in ordinary PostgreSQL rows. Therefore neither an API client nor the current operational message table has a provider URL or a recoverable provider attachment identifier suitable for downloading content. The original source ID may be retained in a protected encrypted capture where the source supplied it; access to such captures does not itself authorize retrieval.

The collector, projector, and API independently apply `safe_attachment_filename` before including an attachment filename as display metadata. It checks Unicode compatibility-normalized and repeatedly percent-decoded forms for paths, URL delimiters, `www.` hostnames, controls, and credential-like assignments, including password and session assignments. It preserves safe literal or benign encoded percent names unchanged and omits unsafe names. A filename is never a storage key, URL, or authorization credential. This filtering reduces disclosure risk; it cannot prove arbitrary source text contains no secret. Attachment locations and provider credentials must not enter ordinary API responses, browser bundles, screenshots, or logs.

A real integration needs, before implementation or enablement:

1. Verify with the authorized provider account how to re-fetch the exact conversation/message/attachment and whether a location is a signed URL, a stable identifier, or requires authentication; document permitted hosts, redirect policy, expiry, deletion and access semantics. The current filtered, non-atomic message collector does not establish complete historical coverage.
2. Select and configure private object storage, an explicit retention/deletion policy, encryption and backup handling, and separate server-side credentials. Do not place source URLs or storage credentials in the repository or browser.
3. Design a durable mapping from the provider source identity to an opaque object key and its owning message/property. Writes must be idempotent and bounded in size, content type and resource use. Recheck source deletion and handle failures without publishing stale or partial content.
4. Authorize each read against the current active user, conversation and property on the server. Stream through an approved bounded endpoint or use narrowly scoped short-lived delivery only after verifying provider/storage behavior; never expose provider URLs. Prevent path traversal, SSRF, redirect abuse, header injection and cross-property access. Log only redacted outcome metadata.
5. Verify with fictional provider/storage fixtures: authorized and denied access, revocation during transfer, malformed and encoded filenames/URLs, limits, duplicate jobs, deletes, retention, backup/restore, failures and token-free logs/responses. Then test with real staging credentials and authorized owners before claiming live retrieval.

No provider download, private-object upload, live integration, or deployment is performed by this branch as part of this preparation.
