# Migration review status

This clean-history branch is a work in progress for code review and transfer. It is not an approved production release. Do not deploy its legacy GitHub Pages files, Firestore rules, or team administration service. The legacy HTML owner, codes and report UID gates intentionally fail closed, and legacy Firebase web configuration must be supplied externally. The API-based pages retain Firebase Authentication and use PostgreSQL authorization; staging account provisioning and real owner sign-in have not been verified.

The release builder currently reports three findings: direct Firestore access in the legacy overview and inbox, and missing API runtime-mode consumption in the legacy inbox. It creates no artifact. API-only overview and inbox candidates are present under `deploy/frontend-api` but are not selected for release. Provider-task discussions require explicitly reviewed bindings; existing source records have not been reconciled to real tasks. Recurring ingestion, complete provider history, attachment retrieval, real Firebase authentication and real property mappings are not verified.

For isolated staging inspection only, `deploy/frontend_build.py --environment preview --review-pages` selects the API candidates and adds a staging notice to every page while retaining the existing source, privacy, and environment-isolation checks. The flag is rejected for production; a successful review build is not evidence of production readiness or permission to deploy. See `DEPLOYMENT_RUNBOOK.md` for separate staging configuration and verification requirements.

The proposed legacy Firestore rules require explicitly provisioned trusted boolean claims. The team administration emulator service requires an explicit server-side owner UID. These changes have only been tested in isolated emulators; never deploy them to production before an approved trusted-claim/bootstrap migration and verification of existing accounts. See `TEAM_PERMISSIONS.md`, `LEGACY_CONFIG_REVIEW.md`, `MIGRATION_RUNBOOK.md` and `DEPLOYMENT_RUNBOOK.md`.

The inbox capture staging command is manual, defaults to dry run, requires collection-only mode and an explicitly reviewed mapping, and does not call the provider or schedule a job. Later provider-capture apply requires a private receipt binding the dry run's inputs, mapping and staging database target; the receipt does not establish human review or completeness. Initial trusted-operator baseline import remains a separate path. Attachment display metadata is filtered, but attachment retrieval is not implemented. PostgreSQL staging, real data, Vercel deployment and VPS services remain separate tasks. Keep outbound messages, calls, device controls, schedules and production cutover disabled until separately approved.

A privacy review replaced source-derived code layouts and thermostat schedules in fixtures with independent fictional examples and removed fixed Firebase identities/configuration. Known-value and source-backed scans are limited and cannot prove absence of unknown secrets or private information. Review all files before making this branch public. The existing public Pages deployment and shared Git history require separate owner remediation; a clean branch does not erase them.
