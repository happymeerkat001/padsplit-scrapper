# Publication checks and history boundary

Run `venv/bin/python -m padsplit_scraper.publication_guard` from the repository root before preparing a public update. The scheduled scraper and local morning/afternoon publication scripts run the same guard before staging their generated files.

The guard checks strict public snapshot schemas, empty room and thermostat records, an empty embedded codes schema, high-confidence credential patterns in public and nonignored source text, and optionally an exact private blocklist. Supply a private UTF-8 file with one known sensitive value per line via `--private-blocklist /private/path/blocklist.txt` or `PUBLICATION_BLOCKLIST_PATH`; values shorter than eight characters are not compared. The file must stay outside the repository and the output reports paths and categories only, never matched values. Git file enumeration must succeed or the guard fails closed. The guard also rejects tracked or staged `.env` files, `.private-config`, raw scraper and thermostat output directories, logs and runtime state, even if forcibly added. After staging, run `venv/bin/python -m padsplit_scraper.publication_guard --check-index` to require no worktree/index differences or nonignored untracked files before relying on the worktree scan for staged bytes. Review the staged file list separately, including any other ignored files added forcibly. This is a focused defense, not a substitute for reviewing screenshots, binaries, unknown secrets, short identifiers or repository history. It does not inspect ignored local credentials or generated raw outputs, which must never be staged.

The existing public `improvement/operations-dashboard` branch descends from an earlier commit containing private messages and populated access fields. Cleaning the current tree does not remove those historical blobs or change the deployed site. A normal incremental push to the already-existing branch does not newly transfer its existing ancestor objects, but leaves them reachable. Confirm exactly which commits and objects a proposed push would add; do not create another public ref that makes previously non-public sensitive objects reachable.

The owner should first contain the current public site and repository exposure, then rotate affected credentials and access codes. A clean publication can be prepared locally from a reviewed sanitized tree as a new root on a separate branch, with no sensitive ancestor. Prefer a separate private repository as the destination until the owner reviews the resulting tree and chooses its visibility. Preparing that local branch does not modify shared history; its publication is a separate owner decision. Removing existing public historical blobs requires a coordinated owner/administrator decision, including treatment of other refs, forks and cached copies; it may require rewriting shared history and force-pushing. This branch does not authorize or perform those actions. An orphan branch alone does not remove the existing public history.
